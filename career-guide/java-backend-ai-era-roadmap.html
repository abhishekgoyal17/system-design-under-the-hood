01Java foundations core

Not "I know Java." I want you to get to "I know why Java behaves the way it does."

Language fundamentals

Start here, even if it feels basic — go back and make sure it's actually solid: variables, primitive vs reference types, operators, control flow, arrays, methods, static, final, this, super. I've interviewed people with three years of experience who fumble the difference between final on a variable vs a method vs a class. Don't be that person.

OOP — actually understood, not memorized

You've heard these words a thousand times: classes, encapsulation, inheritance, polymorphism, abstraction, interfaces vs abstract classes, composition vs inheritance, association, aggregation. Here's what I want from you instead of reciting definitions — take a 3-level inheritance hierarchy you've actually written, and redesign it using composed interfaces, on a whiteboard, out loud. That's the difference between quoting "favor composition over inheritance" and actually owning it in an interview.

Concepts that separate you from a copy-paste developer

  • ✓
    Pass-by-value, alwaysJava passes object references by value. Know exactly what that means when you mutate an object inside a method vs when you reassign the reference.
  • ✓
    String pool + immutabilityWhy String is immutable, what the string pool actually is, and when StringBuilder genuinely matters for performance — not just "always use StringBuilder in a loop" as a rule you memorized.
  • ✓
    == vs equals(), and the equals()/hashCode() contractOverride one, you must override both. Be ready to explain why breaking that contract silently corrupts a HashSet.
  • ✓
    Autoboxing trapsWhy Integer a = 127; Integer b = 127; gives a == b as true, but the same thing with 200 gives false. The integer cache — and why it matters more than it looks like it should.
  • ✓
    Comparable vs ComparatorNatural, built-in ordering vs an external, pluggable one — and know when a class genuinely needs both.

02Collections, deeply core

Most people stop at "I know the interfaces." I want you to go further — this is the single highest-leverage section in this whole guide.

List, Set, Map, Queue, Deque — knowing the interfaces gets you through a basic coding round. Knowing what's happening inside the implementation is what gets you through a system design round, and honestly, through the 2am incident when something's suddenly slow.

ArrayList vs LinkedList

With ArrayList, I want you comfortable talking about the internal array, how resizing works, capacity vs size, why random access is O(1), and the real trade-off on insertion/removal in the middle. With LinkedList, know the node structure and traversal cost — but more importantly, be able to explain why it is not automatically faster than ArrayList for inserts and deletes once you account for cache locality. I see this get flipped backwards constantly, even by people with a few years in.

HashMap — let's actually go granular here

"I know HashMap"
Key → hash → bucket → value. O(1) lookup.
"I understand HashMap"
Hashing, hash function quality, buckets, collision resolution, load factor + resizing + rehashing, treeification into a red-black tree past a threshold, average vs worst-case complexity, why a mutable key silently breaks your lookups.

Here's what I'd actually ask you if we were in a room together: what's the default load factor, and why 0.75 specifically? What happens on resize — is it actually cheap, or does someone eventually pay for it? Why does Java treeify a bucket into a red-black tree instead of leaving it a plain linked list, and at what size does that kick in? And why does using a mutable object as a key set you up for a landmine six months later?

Once that's solid, round out the rest of the family: HashSet internally (it's a HashMap wearing a trench coat — that's genuinely all it is), LinkedHashMap (insertion or access order — this is how you'd build an LRU cache from scratch if someone asked), TreeMap/TreeSet (backed by a red-black tree, sorted iteration), PriorityQueue (a binary heap), ArrayDeque.

Prompt you can reuse

"Quiz me on Java HashMap internals — hashing, collision resolution, load factor, resizing, and treeification — one question at a time, and tell me immediately if my answer is wrong or incomplete before moving to the next one."

03Multithreading + concurrency core

Don't just "learn multithreading" as a topic. I want you to be able to reason about a program that behaves differently every single time you run it.

01

Threads & the basics

Process vs thread, thread lifecycle, Runnable vs Callable vs Future, thread interruption, daemon threads.

02

Synchronization

Race conditions, critical sections, synchronized, intrinsic locks, the monitor, ReentrantLock, ReadWriteLock, StampedLock.

03

Executors

ExecutorService, ThreadPoolExecutor, fixed vs cached thread pools, work queues, core/maximum threads, rejection policies. This is exactly the part you'll come back and rewrite once you start fanning out to slow LLM calls in section 10 — so get it right now.

04

The Java Memory Model

Visibility, atomicity, ordering, happens-before, memory barriers, volatile — and specifically, why volatile int counter++ is not thread-safe even though it feels like it should be. This trips up more experienced engineers than you'd expect.

05

Atomics & lock-free thinking

AtomicInteger/AtomicLong/AtomicReference, compare-and-swap, CAS loops, and the ABA problem.

06

CPU + concurrency — the part almost everyone skips

L1/L2/L3 cache, cache coherence (why one core can see a stale value another core just wrote), and false sharing — two unrelated variables sitting on the same cache line, causing needless invalidation between cores. If you can explain false sharing to me without being prompted, you're already ahead of most senior candidates I've seen.

07

Problems you must be able to reason about

Race condition, deadlock, livelock, starvation, thread contention, lock contention.

Done when
You can explain why a multithreaded program behaves differently from a single-threaded one, and you can reason about correctness, visibility, and performance — not just sprinkle synchronized everywhere and hope nothing deadlocks.

04JVM + performance core

Don't stop at knowing Java syntax — I want you to understand what actually happens once your code starts running.

Class loading: the lifecycle, the ClassLoader hierarchy (Bootstrap → Platform → Application), and the parent delegation model.

JVM memory: the heap (young generation, old generation, allocation), the stack (frames, local variables, stack overflow), metaspace, native memory, code cache.

Garbage collection: why it exists at all, reachability, GC roots, minor vs major/full GC, stop-the-world pauses, generational GC. Then the collectors — Serial, Parallel, G1, ZGC, Shenandoah. You genuinely don't need to memorize every collector's internals, but you should be able to reason out loud about why a production service would pick one over another.

JIT: bytecode turning into native code, hot-method detection, runtime optimization, warm-up — this is exactly why your service feels sluggish for the first few minutes right after a deploy, and it's a great thing to be able to explain when someone asks "why does it feel slow right after we roll out?"

Tools you should actually have opened at least once: JFR (JDK Flight Recorder), VisualVM, thread dumps, heap dumps, profilers.

Done when
You can investigate why a Java service is slow or leaking memory — instead of restarting the pod and quietly hoping it doesn't happen again tonight.

05Spring Boot + framework internals core

Don't stop at @RestController, @Service, @Autowired. I want you to understand what Spring is actually doing underneath those annotations.

Spring Core: IoC, dependency injection, ApplicationContext, BeanFactory, bean scopes, and the full bean lifecycle — creation, injection, initialization, post-processors, destruction.

Dependency injection styles: constructor vs setter vs field injection. Be ready to explain why constructor injection is generally preferred — immutability, testability, and failing fast when a required dependency is missing, instead of finding out at 2am.

Proxies + AOP: JDK dynamic proxies vs CGLIB, advice, pointcuts, aspects. This is what makes @Transactional and @Cacheable feel like magic — right up until you understand it isn't magic, it's a proxy wrapping your bean.

Transactions: @Transactional, propagation, isolation, rollback rules, read-only transactions, and the proxy mechanism underneath — including the classic gotcha of calling a @Transactional method from inside the same class and watching the proxy get silently bypassed. I've seen this exact bug ship to production more than once.

Spring Boot itself: auto-configuration, starter dependencies, profiles, Actuator, health checks.

Done when
You can walk me through what happens, step by step, between "Spring Boot application starts" and "a request reaches your controller" — component scan, context refresh, bean wiring, all of it.

API design: consistent error responses, validation, request/response DTOs, backward compatibility.

07Databases + Hibernate core

This needs to go way beyond "I know SQL." Let's actually get into it.

SQL: joins, GROUP BY / HAVING, subqueries, CTEs, window functions. Indexes: B-tree, composite indexes, covering indexes, selectivity, actually reading a query plan with EXPLAIN ANALYZE instead of guessing — and just as important, knowing when an index quietly hurts your write performance.

Transactions: ACID. Isolation levels: Read Uncommitted, Read Committed, Repeatable Read, Serializable — and which of dirty reads, non-repeatable reads, and phantom reads each one actually prevents. MVCC: how Postgres gives you concurrent reads and writes without locking the whole table.

Hibernate / JPA — go granular here too

Entity lifecycle, persistence context, first-level vs second-level cache, dirty checking, flush timing, lazy vs eager loading, cascades, entity relationships.

The N+1 query problem
What causes it, how to actually detect it — turn on SQL logging and count the queries, don't guess — and the three real fixes: fetch joins, entity graphs, batch fetching. Out of everything on this whole page, this single problem shows up in more production incidents than almost anything else I've dealt with. Take it seriously.

Also make sure you're solid on: optimistic vs pessimistic locking, connection pools, and how transactions interact with Hibernate's session underneath.

Done when
You can diagnose why a database-backed API is slow — instead of reflexively adding an index or bumping the connection pool size and hoping it goes away.

08Distributed systems core

The moment your backend runs across more than one machine, a completely different set of problems shows up — and they're not optional to understand anymore.

CAP theorem: consistency, availability, partition tolerance — and why partition tolerance isn't actually a choice once you're distributed, so the real trade-off you're making is C vs A.

Kafka: producer, consumer, topic, partition, offset, consumer group, ordering (only guaranteed per-partition), replication, retention. Delivery semantics: at-most-once, at-least-once, and exactly-once — and why "exactly-once" in practice really means "effectively-once," achieved through idempotency, not some magic guarantee.

Patterns you should be able to draw from memory: the outbox pattern (so a DB write and an event publish don't quietly drift apart), the saga pattern (choreography vs orchestration, and compensating actions when something fails halfway through), CQRS (separate read and write models), distributed locks, leader election, idempotency and deduplication.

Done when
You can explain what happens when one service, one database, or one network link fails — and what your system actually does about it, instead of just falling over.

09System design + performance core

Now bring everything above together into one skill: taking a service from "it works on my machine" to "it can survive production traffic."

Scalability: vertical vs horizontal, stateless services, load balancing, replication, sharding. Caching: cache-aside, write-through, write-back, TTL, invalidation, cache stampede, cache penetration — with Redis as your reference implementation for most of these.

Latency, not just averages: p50, p95, p99, throughput, QPS/RPS. A service with a great average latency and a terrible p99 is still a genuinely bad experience for a meaningful chunk of your users — don't let anyone hide behind an average.

Reliability: timeouts, retries, circuit breakers, backpressure, graceful degradation. Observability: structured logs with correlation IDs, metrics, and distributed traces — OpenTelemetry ties all three of these together into one picture.

Tools, MCP, and agents

Tool/function calling: the LLM decides what to call, your Java backend executes it, the result goes back to the model. MCP (Model Context Protocol): clients, servers, tools, resources, prompts — the standard way to connect a model to external capability, so you're not reinventing this per project. Agent loop: plan → act → observe → repeat, workflows vs autonomous agents, human-in-the-loop. Borrow this rule from the agent literature and actually apply it: prefer the simplest workflow that solves the problem, and only add autonomy once the task genuinely needs it.

Go deeper — tools, MCP & agents

  • modelcontextprotocol.ioofficial spec — start here, then go to the SDK below.
  • modelcontextprotocol/java-sdkGitHub · 3.7k★ — build MCP clients and servers in plain Java, no framework required.

Evaluation — the skill almost every tutorial skips

Unit tests prove code. Evals measure behaviour on a dataset. Start with error analysis — read real traces, categorize the failures by hand — before you reach for any automation. Evaluate retrieval and generation separately in a RAG system; they fail in different ways for different reasons. If you use LLM-as-judge, calibrate it against a human expert first — don't just trust it because it sounds confident.

Go deeper — evaluation
  • Hamel Husain — "Your AI Product Needs Evals"hamel.dev — foundational, and honestly the single most practical writing on this whole topic.
  • promptfoo/promptfooGitHub · 25.5k★ — a genuinely practical eval and red-teaming tool, the closest thing to "unit tests for prompts" that exists today.

14Three projects that prove it

Don't build twenty demos. Build these three, ship them publicly, and write honestly about what broke.

Project 1 — everyone
Enterprise RAG platform: Spring Boot + Spring AI + pgvector + Redis. Role-based access on retrieval, citations, streaming, a small eval set with retrieval and answer scores.
Project 2 — mid-level and above
AI dev assistant with MCP: "Why did my deployment fail?" — reads commits, checks CI, inspects logs. Tool validation, audit log, human confirmation before any write.
Project 3 — senior / architect
Production AI service: model router with fallback, tool registry, guardrails, cache, cost tracking, tracing and evals. Publish the design doc and the cost model, not just the code.
For every project, publish
A README with an architecture diagram, one honest write-up of what broke, and a measured result — latency, cost per request, eval score. That's the evidence hiring managers actually look for.

"Here's what I'm trying to learn: [topic]. Don't give me a generic roadmap. Instead: break it into sub-concepts, ask me what I already know about each one, point out the gaps based on my answers, and then help me turn those gaps into a short study plan I'll actually stick to."

Final word

Look — frameworks will keep changing. Models will keep improving. Some of what's genuinely hard today will just be a managed service you click a button for next year. But here's what won't change: systems still need to be reliable, secure, observable and affordable, and someone has to be trusted to make that true when the component sitting in the middle is probabilistic instead of deterministic. That someone is a strong backend engineer who actually took the time to learn how AI behaves — not someone who memorized a framework's API before it changed again.

This page can genuinely help you get started, in a lot of ways. But if you take one piece of advice from me on this whole journey of preparation and job switching, let it be this: document your own learning as you go, find your own good resources, experiment, and actually learn from what you find. You will become a far better engineer working with all of it your own way than you ever will just following mine.

Start small. Stay consistent. Build big.
